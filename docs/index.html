Technical Overview

Turning receipts & invoices into a clean asset register — automatically

This system reads a photo or PDF of a purchase document, works out what was bought, matches it to the purchase order it belongs to, decomposes and prices every real item, classifies each one, and writes tidy rows into a database — with a human reviewing rather than retyping. This page explains how, from the ground up, as the pipeline is built today.

1 · The problem it solves

Organisations buy a lot of equipment. Every purchase is supposed to be recorded in an asset register — a table listing each item, its category, quantity and price — so the organisation knows what it owns. Today someone does this by hand: they read a receipt or invoice, work out which purchase order it belongs to, decide what needs registering, type in the details, and try to classify everything consistently. It is slow, error-prone, and inconsistent between people.

This project automates the clerical part and leaves a human in charge of the judgement calls. You upload the document; the system extracts, matches, decomposes and classifies; a reviewer checks the result on screen — with the source invoice, PO and SOW right next to it — and confirms it into the register.

Concrete example. An invoice might contain a single vague line — “Advance payment – equipment package … S$18,750”. Recorded literally, that one row is useless as an asset record. The system instead matches the invoice to its purchase order, breaks the line into the real items (workstation, monitor, UPS, software licence …), prices each one, and presents them to a reviewer as a linked set — not seven line items to retype.

2 · How it works, at a glance

1. Upload

The Streamlit front end sends the file to a small FastAPI. The file is stored in Postgres and a lightweight “job” message is placed on a Redis queue. The caller gets an immediate 201 Created.

2. Process

A background worker picks up the job and runs it through extraction, PO/SOW matching, enrichment and categorization — reporting each stage it enters so the upload screen can show a live checklist.

3. Review & register

The caller polls the job status, then opens a review form pre-filled by the pipeline, tagged by where each field came from. Confirming it writes the row(s) into the asset register.

The whole thing runs locally and offline for the AI parts — extraction, matching, enrichment and categorization all use a self-hosted, OpenAI-compatible vision LLM on the local network, so no document leaves the environment and no external AI keys are needed. Only optional price look-ups touch the public internet.

4 Stage — extract

The document image (PDF pages are rasterised) is sent to the vision model, which returns the line items, the invoice header (invoice/DO numbers, dates, vendor, payment event) and the PO reference the document cites. Quantities are coerced to a whole unit count.

document crawler · app/agents/document_crawler.py
5 Stage — context invoice only

Resolves which PO and SOW the invoice belongs to — not just an exact match on the digits the vision model read, but a five-rung confidence ladder (see §4 below). Then loads the matched PO/SOW text and extracts the procurement header (vendor, contract, project) from the PO.

deepagents + LLM · app/pipeline/enrich.py
6 Stage — enrich invoice only

Uses the matched PO/SOW text as ground truth to turn vague or bundled lines into real, individually priced items:

6a · Detect & decompose

A generic line with an implausibly large price (a bundle) is broken into its real items — checking the PO, then the SOW, then the web. But if the item already exists as an individual item in the SOW at a consistent price, it is kept as-is (no needless splitting).

6b · Split composites

Explicit bundles like “Workstation + Enrolment Scanner” or “Bracket and Enclosure” are split into separate items (separators vary: + / , and & with).

6c · Price

Each item’s unit price is resolved: PO → SOW → query_item_price (a web search tool), retrying when a result is poor.

6d · Cap

The combined value of the parts is scaled so it never exceeds the invoice’s own line total — the pieces can’t be worth more than the whole.

deepagents + LLM · app/agents/categorizer.py
7 Stage — categorize

Each item is assigned one sub-category from the selected system’s editable taxonomy; the main group (Assets / Inventories / Expenses) is derived from it, plus a one-line reasoning.

PostgreSQL · app/pipeline/write.py
8 Stage — write to mar

Document-level fields (invoice/PO/DO numbers, vendor, project, capitalisation date) are stamped onto every record, then validated rows are inserted into the mar asset-register table.

9 Streamlit review screen

Polls GET /api/jobs/{job_id}/status for the live stage checklist, then GET /api/review/{job_id} for a pre-filled review form — each field tagged ai / system / manual — with the source invoice, PO and SOW in a side rail. Confirming calls POST /api/review/{job_id}/complete.

4 · Matching an invoice to its purchase order

app/agents/document_crawler.py answers “which contract is this invoice against?”. It used to be one exact lookup on the digits the vision model read off the page — a single misread digit meant no PO or SOW context at all, and pricing, bundle decomposition and the procurement header all quietly degraded, with nothing in the logs to say why. It is now a ladder that gets more expensive as it goes, and stops as soon as a rung is confident enough:

rung 0the reference matches exactly — no model call at all
rung 1a deepagents agent with five narrow tools, reasoning over the whole PO index
rung 2one non-tool call with the whole index inlined — for models without tool-calling
rung 3pure-Python signal scoring: fuzzy reference + vendor + payment-event amount — no model involved
rung 4no match — the pipeline behaves as it did before context existed

Rung 0 covers the common case, so nothing that already worked got slower. Rung 3 is the load-bearing one and was built first: fuzzy reference + vendor + payment-event amount identifies an order in this corpus with no model involved.

The agent gets five narrow tools and never writes SQL — the whole corpus renders as ~2.5 KB of cards, so there is nothing to search that it cannot read, and no tool returns a document body (the agent picks a reference; code loads the text). Any reference the model returns is checked against the database and dropped if absent — this neutralises hallucination outright — and confidence is recomputed here from the signals that actually verified, not taken from the model’s own certainty (that goes into a reasoning field, nowhere else). Below PO_CRAWLER_MIN_CONFIDENCE the answer is “no match”: a wrong purchase order is worse than none.

PO_CRAWLER=off restores the old exact-match-only behaviour; PO_CRAWLER=deterministic skips both model rungs and uses rung 3 only.

5 · Stage by stage (the technical detail)

Upload API — app/api/routers/uploads.py (FastAPI)

  • POST /receipts and POST /invoice share a handler that stores the file in receipts (a BYTEA blob) and enqueues the job stamped with its type.
  • Returns 201 {job_id, receipt_id, system, type, status:"queued"}. Invalid system → 422.
  • GET /results/{job_id} and GET /api/jobs/{job_id}/status read the published result / live stage (app/api/routers/results.py); GET /health reports DB/Redis.

Queue & worker — Redis + app/pipeline/consumer.py

The job travels through the Redis list object-categorization (the claim-check pattern: the big file stays in the database, only a small pointer goes on the queue). The consumer resolves the file, runs process_job(), and publishes the result three ways (a keyed value with TTL, a pub/sub channel, and an output/{job_id}.json file). It never crashes on one bad message — every failure comes back as a result with status="error".

Stage — extract (vision LLM, app/pipeline/extract.py)

The receipt/invoice image is base64-encoded and sent to a local OpenAI-compatible vision model with a strict JSON instruction. It returns each line item (name, description, quantity, price, serial_no), the invoice header, and the document’s PO reference number. PDFs are converted to page images first.

Stage — context (invoice only, app/pipeline/enrich.py + the crawler)

Resolves the PO/SOW match (see §4), loads their text, and extracts the procurement header (vendor, project, period_contract, purchase_type) from the matched PO — the ground truth used by every step that follows.

Stage — enrich (invoice only)

Three deepagents/LLM steps grounded in the matching PO & SOW, followed by a deterministic cap:

StepWhat it doesHow
detect & decompose Break a generic, implausibly-priced line into its real items — but keep an item untouched if it already matches an individual SOW item at a consistent price. app/agents/decomposer.py; expected price via PO → SOW → query_item_price; only lines above a configurable PRICE_SANITY_THRESHOLD are checked.
splitSplit explicit “A + B” composites into separate products. Single LLM call using the PO then SOW to name components.
priceResolve each item’s unit price. app/agents/pricer.py: PO → SOW → query_item_price (DuckDuckGo via app/tools/web_price.py), with retries.
capGuarantee the parts don’t sum to more than the invoice line total. Proportional down-scaling of unit prices when the combined value exceeds the invoice total.

query_item_price(item_name) searches DuckDuckGo and parses a currency price from the results (returns 0.0 if none found, prompting a retry with a more specific name).

Stage — categorize & write

app/agents/categorizer.py assigns each item exactly one category from the chosen system’s YAML taxonomy; the main group is derived deterministically from that category, and a short reasoning is recorded. app/pipeline/write.py stamps document-level fields onto every record (invoice/PO/DO numbers, vendor, project, a derived asset-capitalisation date, whether the group is taggable) and inserts the final rows into mar.

6 · Two workflows, one pipeline

receipt

POST /receipts

Straightforward. Extract the line items and record them wholesale: extract → categorize → write. No PO/SOW context, no bundle breakdown, no web pricing.

invoice

POST /invoice

The full treatment. Extract → context (match PO/SOW) → enrich (detect & decompose, split, price, cap) → categorize → write. This is where vague, bundled, or oddly-priced lines get turned into real, individually-priced assets.

The single type field on the job message is what routes each upload to the right behaviour; STAGES = ("extract", "context", "enrich", "categorize", "write") in app/pipeline/orchestrator.py is the full list a job can report — a receipt job simply never reports context or enrich.

7 · The front end

The operator-facing UI is a Streamlit app (frontend/streamlit_app) that renders server-side and calls the API by Docker service name (API_BASE=http://api:8000), so the browser only ever talks to the Streamlit container and CORS never comes into it.

Home

Register tiles from GET /api/summary — per-category counts, pending count, last-updated.

Upload

Posts the file, then polls /api/jobs/{job_id}/status and renders the stage checklist live.

Review

A pre-filled form from /api/review/{job_id}; each field tagged ai/system/manual, with source documents in a side rail.

Add asset

A blank form (/api/review/blank) for registering an item by hand, with no job_id.

Each source_documents entry in a review payload carries a kind (invoice/po/sow/do) and the URL that serves it — served by app/api/routers/documents.py, which rasterises a PDF page on request (?as=png&page=N) so the viewer never depends on a browser PDF plugin. A review payload also carries context_match — which PO the crawler tied the invoice to, its confidence, and the evidence — rendered under the PO entry in the rail.

Completing a review (POST /api/review/{job_id}/complete) turns the reviewed line item into the asset (status="Registered"); the invoice’s other line items are linked to it as components via parent_no.

A second, legacy route. GET /app still serves the original Claude-Design export from frontend/, with static/bridge.js injected into the response (the exported HTML on disk is never modified). It is kept as-is; the Streamlit app is the front end actually in use, ported off that export onto the same /api/* routes.

Reference tables — po, sow & po_index

sow.ref_no (the number prefixing each SOW filename) is the primary key. po.ref_no — extracted from each PO’s text by an LLM — is a foreign key to it, modelling many POs → one SOW. po_index is a compact, deterministic index (app/ingest/documents.py + app/ingest/parse.py, regex-based, no model call) built from po.content/sow.content, and is what the document crawler searches. Uploaded files live in receipts.

Systems & editable categories

Two classification systems ship: oxn (categories derived from the project’s policy document) and ehab (a placeholder). Each is a plain YAML file — config/categories.<system>.yaml — of {name, group, code, description}. Editing the YAML changes what the agent may assign; no code change needed.

10 · Notable design choices

  • Async claim-check. The API returns instantly; the large file stays in the database and only a tiny pointer rides the queue — keeping Redis lean and the upload responsive.
  • Local-first AI. Extraction, matching and every agent run on a self-hosted vision LLM — private and key-free. Only optional price look-ups reach the internet.
  • The model never gets the last word. The document crawler checks any PO reference the model returns against the database and drops it if absent; confidence is recomputed from signals that actually verified, never taken from the model’s own stated certainty.
  • A ladder, not a single lookup. PO matching escalates from a free exact match through a deterministic scorer to an agent, only paying for a model call when the cheap rungs are not confident enough — and refuses to match rather than guess wrong.
  • Ground the AI in real documents. Enrichment decisions (what an item is, what it should cost) are anchored to the matched PO and SOW, not guessed.
  • Don’t over-split. An item that already exists as an individual SOW line at a consistent price is kept as-is; only genuinely generic/mispriced bundles are decomposed.
  • Conserve value. Decomposed parts are proportionally capped so they never sum to more than the invoice actually billed for that line.
  • A human confirms, the pipeline doesn’t. Every job lands in a review screen with field-level provenance (ai/system/manual) and the source documents alongside it — nothing reaches the register unreviewed.
  • Editable, not hard-coded. Categories live in YAML; the classification “system” (oxn / ehab) is chosen per upload.
  • Fail soft. Each stage degrades gracefully — a failed agent, web call, or PO match falls back and the pipeline still produces rows rather than crashing; progress reporting itself can never fail a job.
