Technical Overview

Turning receipts & invoices into a clean asset register — automatically

This system reads a photo or PDF of a purchase document, works out what was bought, classifies each item, figures out a sensible price, and writes tidy rows into a database — with no human re-typing. This page explains how, from the ground up.

1 · The problem it solves

Organisations buy a lot of equipment. Every purchase is supposed to be recorded in an asset register — a table listing each item, its category, quantity and price — so the organisation knows what it owns. Today someone does this by hand: they read a receipt or invoice, decide what needs registering, type in the details, and try to classify everything consistently. It is slow, error-prone, and inconsistent between people.

This project automates that clerical work. You upload the document; the system produces the register rows. A person can review the output instead of transcribing it.

Concrete example. An invoice might contain a single vague line — “Advance payment – equipment package … S$18,750”. Recorded literally, that one row is useless as an asset record. The system instead breaks it into the real items (workstation, monitor, UPS, software licence …), each with its own category and a sensible price.

2 · How it works, at a glance

1. Upload

A web request sends the file to a small API. The file is stored in the database and a lightweight “job” message is placed on a queue. The caller gets an immediate 201 Created.

2. Process

A background worker picks up the job, reads the document with a vision model, enriches and classifies the items, and writes the results — all decoupled from the upload so the API stays fast.

3. Retrieve

The worker publishes the finished result back to the queue/database. The caller polls a results endpoint and gets the structured rows that were written to the register.

The whole thing runs locally and offline for the AI parts — extraction and reasoning use a self-hosted, OpenAI-compatible vision LLM on the local network, so no document leaves the environment and no external AI keys are needed. Only optional price look-ups touch the public internet.

4 · Stage by stage (the technical detail)

Upload API — api.py (FastAPI)

  • POST /receipts and POST /invoice share one handler that stores the file in receipts (a BYTEA blob) and enqueues the job stamped with its type.
  • Returns 201 {job_id, receipt_id, system, type, status:"queued"}. Invalid system → 422.
  • GET /results/{job_id} reads the published result; GET /health reports DB/Redis.

Queue & worker — Redis + stage1_extractor.py

The job travels through the Redis list object-categorization (the claim-check pattern: the big file stays in the database, only a small pointer goes on the queue). The consumer resolves the file, runs the stages, and publishes the result three ways (a keyed value with TTL, a pub/sub channel, and an output/{job_id}.json file). It never crashes on one bad message.

Stage 1 — extraction (vision LLM)

The receipt/invoice image is base64-encoded and sent to a local OpenAI-compatible vision model with a strict JSON instruction. It returns each line item (name, description, quantity, price) and the document’s PO reference number. PDFs are converted to page images first.

Stage 2 — enrichment (invoice only, enrichment.py)

Three deepagents/LLM steps grounded in the matching PO & SOW, followed by a deterministic cap:

StepWhat it doesHow
detect & decompose Break a generic, implausibly-priced line into its real items — but keep an item untouched if it already matches an individual SOW item at a consistent price. deepagents agent; expected price via PO → SOW → query_item_price; only lines above a configurable PRICE_SANITY_THRESHOLD are checked.
splitSplit explicit “A + B” composites into separate products. Single LLM call using the PO then SOW to name components.
priceResolve each item’s unit price. deepagents agent: PO → SOW → query_item_price (DuckDuckGo), with retries.
capGuarantee the parts don’t sum to more than the invoice line total. Proportional down-scaling of unit prices when the combined value exceeds the invoice total.

query_item_price(item_name) searches DuckDuckGo and parses a currency price from the results (returns 0.0 if none found, prompting a retry with a more specific name).

Stage 3 — categorize & write

A deepagents agent assigns each item exactly one category from the chosen system’s YAML taxonomy; the main group is derived deterministically from that category, and a short reasoning is recorded. The final rows are inserted into mar.

5 · Two workflows, one pipeline

receipt

POST /receipts

Straightforward. Extract the line items and record them wholesale: extract → categorize → write. No PO/SOW, no bundle breakdown, no web pricing.

invoice

POST /invoice

The full treatment. Extract → enrich (detect & decompose, split, price, cap) using the matching PO & SOW and the web → categorize → write. This is where vague, bundled, or oddly-priced lines get turned into real, individually-priced assets.

The single type field on the job message is what routes each upload to the right behaviour.

6 · Data model

ColumnMeaning / source
Noauto-increment row id

main_categorygroup: Assets / Inventories / Expenses (derived)
sub_categorythe specific category chosen by the agent
reasoningone-line justification for the classification
asset_id, serial_no, location, statusreserved (not derivable from a receipt yet)

Reference tables — po & sow

sow.ref_no (the number prefixing each SOW filename) is the primary key. po.ref_no — extracted from each PO’s text by an LLM — is a foreign key to it, modelling many POs → one SOW. The invoice’s cited PO number is what links an upload to this ground truth. Uploaded files live in receipts.

Systems & editable categories

Two classification systems ship: oxn (categories derived from the project’s policy document) and ehab (a placeholder). Each is a plain YAML file — config/categories.<system>.yaml — of {name, group, code, description}. Editing the YAML changes what the agent may assign; no code change needed.

8 · Notable design choices

  • Async claim-check. The API returns instantly; the large file stays in the database and only a tiny pointer rides the queue — keeping Redis lean and the upload responsive.
  • Local-first AI. Extraction and every agent run on a self-hosted vision LLM — private and key-free. Only optional price look-ups reach the internet.
  • Ground the AI in real documents. Enrichment decisions (what an item is, what it should cost) are anchored to the matching PO and SOW, not guessed.
  • Don’t over-split. An item that already exists as an individual SOW line at a consistent price is kept as-is; only genuinely generic/mispriced bundles are decomposed.
  • Conserve value. Decomposed parts are proportionally capped so they never sum to more than the invoice actually billed for that line.
  • Editable, not hard-coded. Categories live in YAML; the classification “system” (oxn / ehab) is chosen per upload.
  • Fail soft. Each stage degrades gracefully — a failed agent or web call falls back and the pipeline still produces rows rather than crashing.
